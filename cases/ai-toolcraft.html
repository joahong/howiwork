문서를 옮기는 일과, 운영 문의를 줄이는 일

업무 도구가 바뀌거나 조직의 담당 범위가 넓어지면, 기존 방식으로 처리하던 일이 새로운 부담이 되기도 합니다. Confluence에서 Notion으로 문서를 옮기는 과정과 구인자 서비스팀의 문의 운영에서 이런 문제를 마주했습니다.

Claude Code를 활용해 Confluence와 Slack Canvas의 문서 이관 도구, Sustain 문의 분석 대시보드를 직접 구현했습니다. 문서 이관은 여러 부서가 스스로 실행할 수 있는 도구로 제공하고, 문의 분석은 처리 역할과 담당자 배분을 바꾸는 데 활용했습니다.

문서 이관 도구 | 배경과 필요성

구현
약 6시간
개발 도구
Claude Code
기술 스택
Python, Flask, Next.js, React

Notion을 전사 협업툴로 도입하면서 조직에서 10년 넘게 사용한 Confluence와 최근 1년간 사용한 Slack에 쌓인 방대한 업무 자료를 옮겨야 했습니다.

Confluence에 내보내기 기능이 있었지만 원본의 형태를 온전히 유지할 수 없었습니다.

문서 이관 도구 | 해결하려던 문제와 목표

방대한 업무 자료를 몇 번의 클릭으로 옮기되, Notion에서도 원본처럼 활용할 수 있게 하는 것이 목표였습니다. 본문과 첨부파일, 이미지, 표와 코드 블록 같은 서식, 상위와 하위 페이지 구조를 함께 보존하는 데 집중했습니다.

문서 이관 도구 | 구현 방식

본인 계정으로 로그인한 뒤 옮길 Confluence 페이지와 Notion의 목적지를 입력하고 ‘이사 시작’을 누르면 하위 페이지까지 함께 옮겨집니다.

상위와 하위 페이지 관계는 별도로 저장했습니다. 이관 후 Notion에서 위키로 전환하면 도구의 업데이트 기능으로 이 관계를 연결할 수 있게 했습니다. Slack용 도구도 같은 사용 흐름으로 만들었으며 Canvas를 목록에서 고르거나 링크로 지정할 수 있습니다.

문서 이관 도구 | 개발 과정

Claude와 대화하며 요구사항과 사용 흐름을 정리하고 Claude Code로 구현했습니다. 약 6시간이 걸렸습니다. 가장 많은 시간이 걸린 부분은 테스트에서 확인한 실패 사례를 보완하고 결과 리포트를 만드는 과정이었습니다.

처음 이관 기능을 구현한 뒤 실제 업무 자료로 테스트해 보니 파일이 많으면 작업이 중간에 멈추거나 첨부파일 용량 제한 때문에 일부가 옮겨지지 않는 경우가 있었습니다. 어느 부분이 실패했는지 모르면 모든 페이지를 직접 확인해야 했습니다.

그래서 이관 결과를 완료, 일부 완료, 미완료로 구분하고 완료하지 못한 내용과 사유를 결과 리포트에 표시했습니다. 이를 통해 중간에 멈춰도 다시 시작할 지점을 알 수 있었고, 일부만 실패했다면 해당 항목만 확인해 보완할 수 있었습니다.

문서 이관 도구 | 결과

완성된 도구는 누구나 쉽게 실행할 수 있도록 설치형 앱으로 만들고 사용 가이드와 함께 배포했습니다. 가이드에는 상세한 실행 방법과 페이지 수 및 구성에 따른 예상 소요 시간, 오류가 발생할 수 있는 상황, 결과 리포트 확인 방법과 필요한 후속 조치를 담았습니다.

배포 후 제품팀뿐 아니라 사업, 영업 등 다양한 팀의 동료들이 업무 자료를 옮기는 데 활용했습니다. 수백 개 페이지를 일일이 복사하고 붙여넣는 대신 ‘이사 시작’ 버튼을 한 번 눌러 옮기고, 리포트에 남은 실패 항목만 확인해 보완할 수 있었습니다.

개인적으로는 제가 필요한 도구를 AI와 함께 혼자서 처음부터 끝까지 만들어 본 첫 경험이기도 했습니다.

약 6시간 만에 사용 가능한 도구를 구현할 수 있었던 것은, 직접 사용자로서 무엇이 필요하고 어떤 수준이어야 쓸 수 있는지 명확히 알고 있었기 때문이라고 생각합니다. AI가 어디까지 구현할 수 있는지를 아는 것보다, 무엇을 어떤 수준으로 만들어야 실제로 쓰일지를 아는 것이 더 중요했습니다. 해결할 문제와 기준을 알고 있다면, 누구나 필요한 도구를 직접 만들고 같은 문제를 겪는 사람에게 제공할 수 있다는 가능성을 확인한 경험이었습니다.

서스테인 보드 | 배경과 필요성

초기 구현
1일
업무 적용 후 개선
3주
개발 도구
Claude Code
기술 스택
Python, PostgreSQL, Next.js, Recharts

잡코리아와 알바몬의 구인자 서비스를 담당하는 팀을 맡게 되면서, 가장 먼저 발견한 문제는 팀이 고객 문의와 내부 요청에 많은 시간을 쓰고 있지만 어떤 업무가 누구에게 얼마나 쌓이는지 파악하기 어렵다는 것이었습니다. 문의는 Slack과 사내 포털, 개인 DM으로 흩어져 있었습니다.

먼저 문의 접수와 처리 현황을 확인할 공통 기준인 SSOT(Single Source of Truth)를 마련했습니다. 문의 접수는 Slack으로 모으고 내부 요청과 고객 문의를 채널로 구분했습니다. 답변으로 끝나는 일은 채널에서 처리하고, 원인 조사나 개발이 필요한 일은 Notion 인박스에 남겨 진행을 추적했습니다.

이렇게 접수와 처리 과정을 추적할 수 있게 됐지만, 기록이 쌓이는 것만으로는 업무 유형과 담당자별 부담을 파악하기 어려웠습니다. 팀이 바쁜 원인을 확인하려면 문의 내용과 처리 주체를 함께 분석해야 했습니다. 업무 배분을 판단할 수 있도록 SSOT의 기록을 분석하는 대시보드가 필요했습니다.

서스테인 보드 | 해결하려던 문제와 목표

제품 담당자가 판단하고 실행해야 하는 일과 그렇지 않은 일을 구분해, 제품 조직의 리소스가 필요한 곳에 쓰이도록 하는 것이 목표였습니다. 업무가 몰리는 원인과 반복되는 비효율을 확인하고 누가 어떤 일을 맡아야 하는지 판단하려 했습니다.

서스테인 보드 | 구현 방식

Slack에 접수된 문의와 스레드의 처리 기록을 자동으로 모아 대시보드에서 확인하도록 만들었습니다. 기간과 서비스를 선택하면 문의 접수 추이와 처리 상태, 팀과 담당자별 분포를 볼 수 있습니다.

실제 업무 사례를 구체적으로 전달하며 제품 담당자의 판단과 실행이 필요한 문의인지 구분할 기준을 정리하고, 이를 LLM의 분류 지침으로 제공했습니다. LLM이 이 지침에 따라 문의 내용과 스레드의 대화, 처리 결과를 읽고 분류하도록 했습니다. 접수 때 지정된 팀과 실제 처리한 팀은 따로 기록해 어떤 문의가 어느 팀의 업무로 이어지는지 볼 수 있게 했습니다.

필요한 기능과 분석 기준을 정의하고 Claude Code에 구현을 요청했습니다. 코드 작성은 Claude Code가 수행했고, 저는 실제 업무에 맞게 기능과 결과를 검증했습니다.

서스테인 보드 | 개발 과정

Claude Code로 초기 대시보드를 1일 만에 구현하고, 업무에 적용한 뒤 3주간 집계와 분류를 개선했습니다.

집계 결과에 누락과 오류가 반복돼 실제 기록을 하나씩 확인하며 원인을 찾아야 했습니다. 정확하게 대조하기 위해 문의 기록을 일자별로 나누고, 대시보드를 구성하는 단계별 데이터를 놓고 Claude와 오류가 발생한 지점을 역추적했습니다. 그 과정에서 개인과 그룹 멘션의 식별값, 완료 이모지와 이에 반응한 사용자 정보를 기준으로 처리 상태와 담당자를 구분하는 규칙을 찾았습니다. 이를 Slack 채널의 관리 규칙으로 정리해 구성원들에게 전파하고, 규칙이 반영된 기록을 다시 분석했습니다. 규칙을 찾고 실제 운영에 적용한 뒤 결과를 검증하는 과정을 반복하면서 집계와 분류를 개선하는 데 많은 시간이 들었습니다.

서스테인 보드 | 결과

분석 대상인 구인자 서비스 문의 중 약 37%는 이미 정해진 정책을 안내하는 일이었습니다. 지원 조직이 답변할 수 있는 문의도 제품 담당자에게 들어오면서, 정책 안내와 제품의 판단 및 실행이 필요한 업무가 같은 담당자에게 쌓이고 있었습니다. 이 부담을 줄이려면 각 팀이 맡을 역할을 명확히 하고, 지원 조직이 직접 답변할 수 있는 조건도 갖춰야 했습니다.

그래서 정해진 정책의 안내는 지원 조직이 맡고, 제품 조직은 정책과 기능에 대한 판단과 실행에 집중하도록 부서 간 책임을 정리했습니다. 지원 조직이 직접 답변하는 데 필요한 내용을 함께 확인하면서, 현행화가 필요한 정책서를 정비하는 일을 제품 조직의 지원 과제로 도출했습니다. 반복되는 안내를 줄일 수 있도록 정책서 기반 자동 답변 에이전트도 후속 과제로 구체화했습니다.

담당자별 업무량도 확인할 수 있게 되면서 팀 안에서는 실제 운영 업무량을 근거로 담당 범위를 재조정했습니다. 이후에도 특정 팀원에게 일이 몰리는지 대시보드로 살펴보며, 문제가 커지기 전에 업무 배분과 지원 방안을 논의할 수 있게 됐습니다.

이처럼 업무를 조정하는 데 필요한 근거를 AI로 직접 만든 도구에서 얻을 수 있었습니다. 데이터팀이나 엔지니어에게 별도로 구현을 요청하지 않고도, 오랫동안 막연하게 느끼던 업무 부담을 분석하고 그 결과를 일하는 방식의 변화로 이어갈 수 있었다는 점이 가장 큰 성과였습니다.

개별 도구에서, 팀이 반복해서 사용할 업무 기준으로

도구를 만드는 것과 함께 PO 문서 작업에도 재사용할 기준을 정리했습니다. 문제 분석에서 1-pager, PRD, 유저 스토리와 실험 계획으로 이어지는 흐름을 스킬 11종과 참조 자료 22종으로 구성했습니다. 앞에서 정의한 문제와 다음 문서의 요구사항이 이어지는지, 결과를 검증할 수 있는지 점검하도록 했습니다.

스프린트 운영은 별도로 직접 작성한 문서와 템플릿에 담았습니다. 계획에서 목표와 완료 기준을 합의하고, 작업의 담당자와 기한을 정하며, 리뷰 결과를 다음 개선으로 연결하도록 했습니다. AI를 활용한 문서 작업과 사람이 합의해야 할 협업 기준을 각각의 용도에 맞춰 정리했습니다.

스프린트 운영 키트에 남긴 협업 기준

계획, 데일리, 리뷰와 회고의 진행 방법을 문서와 템플릿으로 작성했습니다. 팀마다 조정해서 쓸 수 있도록 운영 기준을 정리했습니다.

스프린트 운영 키트에 남긴 협업 기준

문서 이관에서는 페이지 생성이 끝나도 누락 확인과 관계 복원이 남았습니다. 문의 분석에서는 집계가 끝나도 처리 책임과 업무 배분을 바꿔야 했습니다. 두 경우 모두 도구의 출력만으로 업무가 끝나지 않았습니다.

AI를 활용해 직접 구현할 수 있게 되면서, 요구사항을 전달하는 데서 나아가 실제 사용 결과를 확인하고 도구를 고치는 일까지 맡았습니다. 자동화할 범위와 사람이 이어 맡을 일을 함께 설계하고, 그 결과를 운영 방식에 반영하는 것을 도구의 완료 기준으로 삼았습니다.
